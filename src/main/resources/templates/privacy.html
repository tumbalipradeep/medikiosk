Privacy & data handling

What MediKiosk does with patient information

This page describes the data-handling behaviours that are actually implemented in the application — not aspirational policy.

Identity & consent

  • ✓ Local kiosk identity. This deployment uses a local, non-ABHA identity. It is not linked to the ABHA ecosystem.
  • ✓ Explicit consent. A patient grants consent for in-clinic processing before the intake conversation begins, and the consent is recorded.
  • ✓ No ABDM / HIS transmission. Nothing is transmitted to ABDM or an external hospital information system in this deployment.

Collection, storage & access

  • ✓ Purpose-limited. Answers, documents, and findings exist to build a clinical case for physician review.
  • ✓ Role-gated reading. Patient, physician, and admin roles can only reach the data their role is authorized to see; this is enforced in the backend.
  • ✓ Document handling. Uploaded reports are content-validated and stored via a secure storage handler; extractable text is processed by PDFBox only.
  • ✓ Audit trail. Significant actions write a persisted audit event that an administrator can inspect.

Technical privacy controls

  • ✓ Referrer policy. Pages send a no-referrer policy so clinical page references are never leaked to third-party origins.
  • ✓ No secrets in the repository. Provider credentials are read from environment variables only; the application contains none.
  • ✓ Preference storage is local. Appearance and motion preferences are stored in the browser only and never sent to the server.

Important scope note

MediKiosk is a demonstration platform for the SIH26047 problem statement. Consent in this model governs in-clinic processing only. A future external integration must enforce its own sharing authorization before any data leaves the kiosk — it can never rely on kiosk consent alone.
