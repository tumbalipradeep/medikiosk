# M5.2 Physician + Interoperability + Clinical Trust — Audit & Design

Internal engineering audit and implementation record for M5.2 of the MediKiosk
project (SIH26047). This document records the state before M5.2, the problems
found, the design decisions taken, and the resulting implementation. It is an
engineering working document, not user-facing.

Baseline: `4e05681` (M5.1), 597 tests, 0 failures / 0 errors / 0 skipped.

---

## 1. Audit findings (Phases 1–19)

### 1.1 Physician workspace (Phase 1, 15)

**G1.** `/physician/home` is a placeholder with a stale "will be added later"
message. There is no dashboard listing completed cases.

**G2.** `/physician/review` shows only the latest completed case, not a
per-case workspace. A physician cannot navigate to a specific older case. There
is no `GET /physician/cases/{caseId}` page.

**G3.** The review interaction is UI-only (in-page counter, no persistence).
A page reload loses all review progress.

**G4.** The review page does not distinguish provenance categories:
patient-reported, AI-reworded, translated, deterministic, document-derived,
physician-entered.

**G5.** Red flags are not surfaced anywhere in the physician UI.

**G6.** The patient identity section does not clearly label the demo/local
identity or the ABHA-ready boundary.

**G7.** The stale "Checkpoint 1" text appears in `app.js` (footer metadata).

**G8.** The shared nav fragment has no role-aware home link; physicians must
know the URL.

### 1.2 Clinical trust model (Phase 2, 16)

**G9.** Physician workspace answers show only question text + answer; the
original displayed wording (possibly translated or AI-reworded), the question
source, the answer source (typed/voice), the language, and the canonical
English question are all missing.

**G10.** Document findings have honest extraction caveats in modals but no
provenance distinction on the main workspace page.

### 1.3 Review model (Phase 3)

**G11.** There is no accept / amend / reject persistence model. Amending
and rejecting are UI-only and lost on reload.

### 1.4 Provenance (Phase 4)

**G12.** Provenance data (question source, answer source, language, displayed
text) is captured in the persisted answers and in FHIR answer observations but
is not surfaced in the physician UI.

### 1.5 Red flags (Phase 5)

**G13.** Flags are computed at conversation time but not persisted; they are
returned to the patient frontend in the conversation response and re-derived
for the patient review endpoint. The physician has no access to flags at all.

**G14.** The patient-facing red-flag banner says "Flagged for clinical
review" (good), but the physician has no way to see or acknowledge the flags.

### 1.6 Document intelligence (Phase 6)

**G15.** The document workspace table shows extraction status and findings
counts honestly. The modals carry extraction caveats. No significant
document-trust problem exists in the physician UI; the findings disclaimer is
already honest ("automatically extracted — may contain errors and must be
clinically verified").

### 1.7 Timeline (Phase 7)

**G16.** The timeline is deterministic, ordered correctly, and preserves
source snippets. Dates that are absent do not receive invented dates. No
significant problem exists.

### 1.8 FHIR quality (Phases 8, 9, 10)

**G17.** `FhirDocumentMapper.toLabObservation` receives `document` and uses it
to build the lab composite id; the parameter is required and the mapping is
correct. No issue.

**G18.** The FHIR export UX is a raw JSON endpoint with no physician-facing
explanation; the physician has no in-page guidance about what the FHIR export
represents or that no external ABDM transmission occurs.

**G19.** `FhirBundleValidator` logs issues but does not block export; this is
documented and correct. No structural weakness found.

**G20.** Deterministic byte-for-byte repeat-export is verified by tests.
No issue.

### 1.9 Audit events (Phase 11)

**G21.** Only `FHIR_EXPORT` events are recorded. No audit events are
generated for physician review decisions (accept / amend / reject).

**G22.** If the `FhirExportTransport` throws a runtime exception before the
success audit event, no failure audit event is written (exception propagates
without audit). This is an audit gap for observable internal export failures.

### 1.10 Consent boundary (Phase 12)

**G23.** Kiosk consent and external interoperability authorization are not
explicitly distinguished in the physician UI; the consent list does not state
whether any kiosk consent constitutes external authorization.

### 1.11 ABHA / identity (Phase 13)

**G24.** The patient identity is local/demo. The `PatientIdentityProvider` is
honest. The physician workspace has no identity section showing the ABHA-ready
boundary label.

### 1.12 HIS boundary (Phase 14)

**G25.** The `his` module is a package-info placeholder with no code. There is
no transport abstraction or deterministic local/no-op implementation to
document.

### 1.13 Data integrity (Phase 19)

**G26.** A `physician_review_entries` table does not yet exist. There is
no persistence model for review decisions. Adding one requires a Flyway
migration (V14) and FK to `completed_cases`.

### 1.14 Security (Phase 18)

**G27.** No IDOR or missing-access-test issues were found in the current
implementation. The `SecurityConfig` role boundaries are intact. The review
POST endpoints (new in M5.2) must have their own role / CSRF test coverage.

## 2. Design decisions

| # | Decision | Rationale |
|---|----------|-----------|
| D1 | New `physician/dashboard.html` + `physician/case.html` replace `physician/review.html`. | Dashboard solves G1/G2; per-case workspace solves G2/G3/G4. |
| D2 | `PhysicianReviewController` GET `/physician/review` becomes a redirect to `/physician/home`. | Preserves bookmark compatibility; all review content moves to per-case workspace. M5.1 tests rewritten. |
| D3 | Review decisions persisted in `physician_review_entries` (unique on case_id, answer_order). | Source-evidence → decision → reviewed representation model; survives reload (G11). |
| D4 | Provenance surfaced from persisted `CompletedCaseAnswerEntity` fields (displayedText, questionSource, answerSource, language, questionText). | No new capture logic needed; the data was already recorded (G9, G12). |
| D5 | Flags are re-derived deterministically from persisted verbatim answers via `RedFlagEvaluator`. | No new persistence table; deterministic and auditable; rules and answers together reproduce the same flags (G13/G14). |
| D6 | `AuditEventType.PHYSICIAN_REVIEW` added; audit event recorded per review decision. | Solves G21. |
| D7 | FHIR export wrapped in try/catch; failure audit event written before propagating 500. | Solves G22. |
| D8 | `ConsentBoundaryService` returns `isExternalTransmissionConfigured = false`. | Explicitly distinguishes kiosk consent from external authorization (G23). |
| D9 | `HisIntegrationBoundary` interface + `LocalOnlyHisIntegrationBoundary` no-op component. | Clean boundary with documented deterministic no-op behavior (G25). |
- D10 is obsolete. #[G17] was audited as correct and required, so no mapper change was made.
| D11 | Nav fragment gets role-aware home link (patient → `/patient/home`, physician → `/physician/home`). | Solves G8. |

## 4. Clinical-safety improvements

- **Provenance surfaced**: physician sees "patient reported", "typed",
  "voice-transcribed", "translated wording", "AI-reworded", "deterministic"
  per answer.
- **Red flags visible**: physician sees flagged items with the triggering
  answer, severity, and honest "system-generated · clinical review required"
  wording (never diagnosis).
- **Source evidence preserved**: amend / reject decisions are stored
  alongside the original answer; original patient answer is never overwritten.
- **Unsafe UI wording avoided**: flags use "Potential concern identified from
  patient response — clinical review required" language, not "Patient has X".
- **Document findings caveat**: "Automatically extracted — may contain errors
  and must be clinically verified" retained in all document modal footers.

## 5. Interoperability improvements

- **FHIR export UX**: physician workspace explains what the bundle represents,
  that it is a local projection, and that no ABDM transmission occurs.
- **Consent boundary explicit**: `ConsentBoundaryService` documents that kiosk
  consent ≠ external transmission authorization.
- **HIS boundary documented**: `LocalOnlyHisIntegrationBoundary` deterministic
  no-op with future adapter point.
- **FHIR validator strengthened**: provenance note required on answer
  observations; deterministic export byte-equality preserved.

## 6. Security improvements

- Review decisions require `ROLE_PHYSICIAN` (`/physician/**` path rule).
- Review POST requires CSRF token.
- Audit events for all review decisions (reviewer attribution).
- FHIR export failure audited before propagating 500.
- No clinical data in audit records.
- Patient cannot access physician endpoints (existing + new regression tests).

## 7. Honest limitations carried from M5.1

- Red-flag detection matches English keywords only.
- No real ABHA/ABDM integration (local/demo identity, no-op transport).
- AI wording offered only in English; non-English uses curated offline
  translations only.
- No handwritten OCR (scanned PDF extraction unavailable).
- No autonomous diagnosis, vitals, medications, or clinical findings
  fabricated.
